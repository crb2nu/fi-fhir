- Why:
  - Tasks 3, 4 and 6. The day-1 gate measured a zero; this inverts it.
- Evidence, and two corrections to `.loom/33` that came out of measuring:
  - **The durable alloc signal is NOT bit-identical, unlike the legacy set.**
    `.loom/33`'s option A rests on `benchmark_util.go:321-327`, which reports
    bit-identical allocation counts across 78-87 artifacts. That was measured on
    pure-CPU micro-benchmarks. A database-backed path is stable but not exact.
    Measured over three runs at `-benchtime=300x`:

    | benchmark | run 1 | run 2 | run 3 | spread |
    |---|---|---|---|---|
    | `IngressSubmit` | 4643 | 4642 | 4641 | 2 (0.04%) |
    | `MLLPSubmit` | 4694 | 4692 | 4693 | 2 (0.04%) |
    | `IngressSubmitParallel` | 4715 | 4703 | 4702 | 13 (0.28%) |
    | `MLLPSubmitParallel` | 4787 | 4755 | 4746 | 41 (0.86%) |

    So: **gate the serial pair, leave the parallel pair report-only.** The
    parallel figure is partly a property of goroutine scheduling — how many
    pooled connections open, how work interleaves — not only of the accept path.
    A regression shows up in the serial pair with a tenth of the noise.
  - **`-benchtime` must be pinned, and this is the load-bearing detail.** At
    `-benchtime=50x` the same benchmarks spread four times wider, because pool
    growth and driver setup are amortized over fewer operations. With the default
    *time*-based budget, a fast runner completes more iterations than a slow one
    and reports a different `allocs/op` for identical code — silently
    reintroducing the hardware dependence the allocation signal exists to avoid.
    `DurableBenchtime = "300x"`; the Makefile target and the CI job both pin it.
  - The kill-test caught this itself: its first version used `testing.Benchmark`
    (time-based N) and failed with 5659 then 4730 — a 20% swing. It now counts
    `runtime.MemStats.Mallocs` over a pinned 300 submissions after a 50-message
    warmup.
  - **Detection floor, stated rather than implied.** With a ~4650 baseline and
    ±2 spread, a ~1% ceiling detects a regression of roughly 40 allocations per
    message. It does not detect one extra allocation per message — nothing gating
    a database-backed path at this baseline could. `.loom/33`'s acceptance
    criterion ("a deliberate extra allocation ... turns the blocking job red")
    is not achievable as literally written; the realistic regressions it is aimed
    at (a struct per segment, a slice per field) are tens to hundreds.
  - Proof of subject: every benchmark asserts one `integration_receipts` row per
    iteration and zero delivery rows. The legacy engine writes no SQL, so a
    non-zero receipt count is what distinguishes the durable path from it. A
    benchmark that silently short-circuits still produces a plausible ns/op —
    that is exactly how the deleted loadtest reported "100% of target".
  - Negative controls, all verified: an inflated `allocs/op` in the artifact →
    `bench-check -set=durable` exits 1 with the offending name; `-set=bogus` →
    exit 1; the legacy set still passes unchanged over its own package list.
  - `golangci-lint` 0 issues with and without `-tags=integration`;
    `go test ./cmd/bench-check/ ./internal/workflow/` green;
    `go test -tags=integration ./internal/integration/perf/` green.
- Caveat carried forward:
  - The ceilings (4700, 4750) are calibrated from **local** runs against
    PostgreSQL 16 on the remote Docker context, not from three CI artifacts as
    task 4 asks. Allocation counts are CPU-independent, which is what makes a
    local baseline legitimate where a local *latency* baseline would not be — but
    a CI service container may still differ. First green CI run should be fed to
    `make bench-durable-calibrate` before the gate is trusted to block.
