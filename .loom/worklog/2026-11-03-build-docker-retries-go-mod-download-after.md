### 2026-11-03 - build:docker retries go mod download after proxy.golang.org stream resets

- What changed: the `Dockerfile` builder stage wraps `go mod download` in a bounded retry (three attempts, 5 s then 10 s backoff) and prints the attempt counter on every outcome, so a job trace shows whether the retry path fired. One changelog fragment (`changelog.d/ci-build-docker-go-mod-download-retry.fixed.md`). No job definition changed: `build:docker` is defined in `.gitlab-ci.yml`, not under `ci/`, and `scripts/ci-job-inventory.sh --check` still reports 77 jobs in sync.
- Why: three `build:docker` runs died about 16 s into `go mod download` on 2026-11-03 with the same signature, `read "https://proxy.golang.org/<module>/@v/<version>.zip": stream error: stream ID N; INTERNAL_ERROR; received from peer` — merge-train pipeline 37258 (MR !290), merge-train pipeline 37313 (MR !292), and merge-request pipeline 37378 job 460747 (MR !294), all on the `ci-7900xtx` runner. The module varies (otel v1.45.0 in 460747), the reset does not. The Mills queue evicts a train row on any failed gating job, so one network blip cost a full readmit. platform/gitops !1050 (merged 2026-11-03) added `build:docker` to `merge_queue.flake_retry.jobs`; that covers trains only, not merge-request head pipelines, and a retry still pays a full rebuild. This entry is the repository-side half.
- Options weighed: (1) a retry loop in the Dockerfile — chosen. It is self-contained (CI, local builds, any future builder), and Go only moves a module zip into `/go/pkg/mod` once it is complete, so a retry re-fetches only what the reset cut off. (2) A BuildKit cache mount for `/go/pkg/mod` — rejected: the job builds through its own `docker:24-dind` service (`DOCKER_HOST=tcp://localhost:2375`) whose state dies with the job pod, and the `BUILDKIT_HOST`/`BUILDKIT_CACHE_PREFIX` exported in the before_script are not consulted by this `docker build`, so the mount would never be warm. (3) A `GOPROXY` fallback — not added: `https://proxy.golang.org,direct` is already Go's default and the `,` form only falls back on 404/410; the `|direct` form would turn every mid-zip reset into a git clone of the module from GitHub, which is heavier and slower than a second attempt against the same proxy. (4) The committed `.tmp/go-mod-cache/` — not used: the 2026-09-24 decision keeps it for the offline HL7 validator, `.dockerignore` excludes `.tmp/`, and it is not an image module source.
- Follow-up worth its own slice: pipeline-level `GOPROXY` already points at the in-cluster Athens proxy with `|` fallbacks (`.gitlab-ci.yml:92`), but nothing passes it into the image build (no `--build-arg GOPROXY`, no `ENV`), so the builder stage talks to proxy.golang.org directly with Go's defaults. Threading it through would make repeat builds hit Athens' module cache instead of the public proxy, but it needs a `.gitlab-ci.yml` edit (a Mills-protected path, like `Dockerfile`) and a kill-test that the `--network=host` build container resolves `athens.ci.svc.cluster.local` from inside dind.
- Evidence: fault injection on the `7900xtx` Docker context against a scratch copy of the Dockerfile whose first attempt is `timeout 4 go mod download` (the provocation never entered the tree): the build log shows `Terminated` at 4.1 s, then `go mod download: attempt 1/3 failed; retrying in 5s`, then `go mod download: succeeded on attempt 2/3` at 156 s, and the builder stage went on to compile the binary. A control build of the unmodified Dockerfile on the same host shows `go mod download: succeeded on attempt 1/3` at 94 s and produced the full two-stage image. The merge-request pipeline on branch `claude/confident-goldstine-64817c` and the Mills train pipeline (`mills-mq/train-libs-fi-fhir-<iid>-<sha>`) carry the same counter line in their `build:docker` traces.
- What's next: watch whether the gitops !1050 flake retry on `build:docker` still fires now that the Dockerfile absorbs single resets; if it does, a reset outlasted two backoffs and the Athens pass-through above is the next step. All three failures were on the physical `ci-7900xtx` lane; the physical lanes have a documented link-flap history that flushes masqueraded conntrack (gitops !814, 2026-09-26, diagnosed on radeonvii), which is what an HTTP/2 stream reset mid-zip looks like from inside a build — unverified for the 7900xtx host.
